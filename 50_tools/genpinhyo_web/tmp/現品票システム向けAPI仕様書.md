# 現品票システム向け 読み取りAPI 仕様書（Django 側）

作成日: 2026-10-23
目的: Django（業務ポータル `03_PFW_Django`）に読み取り専用の API を追加する。
現品票システム（`90_tools/50_tools/genpinhyo_web`）が KRD の SQLite（`krd_machine.db`）の代わりに、この API からデータを取るようにする。

この文書は、Django を修正する別セッションへの引き継ぎ資料です。
「1. 経緯」と「2. 決定事項」は利用者と確認済みの内容です。

## 1. 経緯

### 1-1. なぜ作るか
- 現品票システムは、KRD（加工機スケジューラ）の MySQL を読んでいた。2025-11-22 に、MySQL を写した SQLite（`\\esrv11\KakouDenpyo\krd_machine.db`）を読む形へ移った。
  - 写しを作っているのは `90_tools/15_krd_machine`（Docker・cron）。
- **KRD の MySQL は廃棄される予定**。廃棄すると SQLite の写しも更新されなくなる。
- SQLite の KRD は、現品票システムを動かすためだけに存在している。
- 必要なデータは、Django の次のアプリがすでに持っているか、作れる。
  - 加工スケジュール作成（`apps/machining_schedule`）
  - 工程図管理（`apps/kouteizu`）
- そこで、現品票システムは Django から取ることにした。

### 1-2. DB を直接読まず API にする理由（2026-10-23 利用者と合意）
- **テーブルの作りに縛られないため。** 作業計画（`WorkPlanRow`）は仕様書上「仮」で、項目が変わりうる。API なら、返す形（約束）を守れば中は直せる。
- **本番 PostgreSQL の接続情報を、現品票の PC に配らずに済むため。**
- **組み立ての処理を Django 側に寄せられるため。** 工程の連番付け、品目CDの変換、VER の補い、図番の前詰めがこれに当たる。
- 社内に前例がある。集約注文書の読み取りAPI（`purchase_order:api_mappings`）を、i-Reporter がこの方式で使っている。
  - ただし、あちらは API キーで守っている。こちらは**キーレス**にした（D13）。

### 1-3. 現品票システムが KRD から読んでいるもの（調査結果）
SQLite の KRD は約52テーブルある。現品票が読んでいるのは次の6テーブルだけ。

| KRD のテーブル | 現品票での用途 | 使う画面 |
|---|---|---|
| `DATA_ASP2_PUT` | 伝票No → 工程VERSION（使うのは `SLIP_NO` と `VERSION` だけ） | 現品票発行（メイン）・夜間処理 |
| `MSTR_PROCODESTR` | 部番＋VERSION → 工程文字列（例 `B1-G1-L1-G2`） | 現品票発行・手入力発行 |
| `DATA_KOUTEIZUKAN` | 部番 → 図番 | 現品票発行・手入力発行・チェック項目入力 |
| `MSTR_METAL` | 部番 → メッキかどうか（印字は「1 のときだけメッキ」） | 現品票発行 |
| `DATA_RES_CAPA` | 部番＋VER＋工順 → 工程・資源CD | チェック項目入力（`check_input` と旧版 `pages/4`） |
| `MSTR_RES` | 資源CD → 加工機名 | チェック項目入力 |

詳細: `genpinhyo_web/tmp/KRD_SQLite_利用テーブル整理.md`

## 3. API 共通の決まり

### 3-1. 置き場所（疎結合ルールに合わせる）
- **データを持っているアプリに、それぞれ API を置く。**
  - 作業計画・品目工程・資源・メッキは `apps/machining_schedule` に置く。
  - 工程図は `apps/kouteizu` に置く。
- 一方のアプリが他方を import しないこと（`03_PFW_Django/CLAUDE.md` の疎結合ルール）。
- URL は各アプリの `urls.py` に足す（URL名は下の表のとおり）。

### 3-2. 認証（**キーレス**。2026-10-23 変更）
- ⚠ **ログインも API キーも不要**（利用者の決定 2026-10-23「キーレスでOK」）。
  - 当初は `X-API-KEY`（設定 `GENPINHYO_API_KEY`）で守る案だったが、やめた。
  - 理由: 返すのは図番・工程・VER・加工機名・メッキ有無だけで、守る必要が無いため。
  - 現品票側は、ヘッダーを付けずにそのまま呼べばよい。
- `@login_required` は付けない。
- **`settings.APP_ACCESS_EXEMPT_URL_NAMES` に、全エンドポイントの URL名を追加する。**
  - 足さないと利用権限のミドルウェアに止められる。
  - 現状、未ログインは素通りなので実害は出ない。ただし、規約上は追加が必要。

#### 参照できる範囲と前提（2026-10-23 利用者と確認）
- **Django の外のプログラムから呼ぶための API**。
  - 現品票の PC 以外でも、社内LANの PC・サーバーからならどこからでも呼べる。
  - 呼び出し先は業務ポータルと同じホスト（`http://pfw-gyomu/...`。Nginx Proxy Manager 経由）。
- **社外（インターネット）からは届かない**（業務ポータル自体が社内向け）。
- **守りは無い**。社内LANからは誰でも読める。
- **読み取り専用**。API から Django のデータを書き換えることはできない。
- ⚠ 通信は **暗号化されていない http**。社内LANの中では、中身が平文で流れる。
  - 返す中身は図番・工程・VER・加工機名・メッキ有無だけで、個人情報や金額は含まない。
  - ⚠⚠ **誰でも読めるので、個人情報や金額を返す項目を、あとから足さないこと。**
    足したくなったら、そのときに認証を付け直す。
- キーが無いので、キーをそろえる運用（`.env` と現品票側の同時変更）は**不要**。

### 3-3. 形式
- 文字コードは UTF-8 の JSON。
- 一覧系は `{"count": 件数, "rows": [...]}`。
- POST（一括で引く系）は、**CSRF の対象外**にする（`csrf_exempt`）。外部のプログラムが CSRF トークンを持てないため。
- 空欄は `""` で返す（`null` を混ぜない）。例外は、数値の項目で値が無いときの `null` だけ。
- **読み取り専用。** DB に書く処理を入れない。

## 4. エンドポイント

### 4-A. `apps/machining_schedule`

#### A1. ロットごとの VER・工程文字列・メッキ（`DATA_ASP2_PUT`＋`MSTR_PROCODESTR`＋`MSTR_METAL` の代わり）
現品票発行のメイン処理が使う。現品票側は、加工伝票の行（伝票Ｎｏ・加工部番）をまとめて送る。
Django は VER・工程・メッキを解決して返す。

- `POST /machining-schedule/api/genpinhyo/lots/`（URL名 `machining_schedule:api_genpinhyo_lots`）
- 送る内容: `{"lots": [{"lot_no": "H000037264", "hmcd": "740-409CA300"}, ...]}`
  - `hmcd` は現品票が持っている加工部番。**rBOM の品目CDのままの形**（変換前）。
  - 件数は数千（いまの加工伝票CSVで約8,700行）。1回で受け付けられること。
- 返す内容: 1ロット1行。

| 項目 | 中身 |
|---|---|
| `lot_no` | 送られたロット番号 |
| `hmcd` | 送られた加工部番（そのまま） |
| `setu_f` | 変換後の品目CD。`pipeline.convert_hmcd_to_setu_f` を通したもの（例 `740-409CA30`） |
| `version` | VER（下の決め方） |
| `version_source` | `work_plan`（作業計画にあった）／`priority`（優先VER）／`default`（どちらも無く 1） |
| `process_str` | 工程文字列（連番付き。下の作り方）。品目工程マスタに無ければ `""` |
| `is_plating` | メッキマスタで「メッキあり」なら `true`、それ以外（メッキ無し・未登録・登録なし）は `false` |

- **VER の決め方**
  1. 作業計画（`WorkPlanRow`）に同じ `lot_no` があれば、その `version` を使う。
     - マシニング課が画面で選び直した値も、そのまま出る。
  2. 無ければ、`setu_f` の優先VER（`PriorityVersion`）を使う。
  3. それも無ければ `1`。
  - 2〜3 は、作業計画の取り込み時の初期値（`views._initial_version`）と同じ決まり。
    **同じ決まりを2か所に書かないこと**（関数を共有するか、services に寄せる）。
  - ⚠ 作業計画は「取り込み時点の伝票」しか持たない。取り込みはいま手動のボタン。
    取り込み前の新しい伝票は 2〜3 になる。
- **工程文字列の作り方**（`MSTR_PROCODESTR` と同じ形）
  - 品目工程マスタの、同じ `final_item_code`（＝`setu_f`）・同じ `version` の行を使う。
    `process_order` が空欄の「新規登録が必要」行は除く。
  - 並びは **工順 → 工程CD の昇順**（作業計画の一覧の「工程」列と同じ並び）。
  - 工程CDごとに、**出てきた順の連番**を付けて `-` でつなぐ。
    例: B, G, L, G → `B1-G1-L1-G2`。MC だけなら `MC1`。
  - 根拠: KRD の写しで、この作り方で 4,439件中 4,436件が `MSTR_PROCODESTR` と一致した。
    残り3件は KRD 側の表どうしの更新ずれ。
  - ⚠ 作業計画の一覧の「工程」列は連番なし（`B-G-L-G`）。**こちらは連番付き**。一覧の表示は変えない。
- **メッキの判定**
  - `PlatingRow.item_code == setu_f` で、`is_plating is True` のとき `true`。
  - ⚠ `$$` を含む行の扱いは「6. 要確認事項」の Q1。
- 補足: 現状の現品票は、加工部番（変換前）で KRD を引いている。そのため `-405`/`-409`/`-410` の3桁形の部番（2026年1月の写しで70部番）は、工程もメッキも引けていない。`setu_f` で引くことで、これも直る。

#### A2. 工程文字列の一覧（`MSTR_PROCODESTR` の代わり）
手入力発行の画面が使う。部番を入れると、その部番の全VERの工程を出す。

- `GET /machining-schedule/api/genpinhyo/process-strings/`（URL名 `machining_schedule:api_genpinhyo_process_strings`）
- 引数: `item`（省略可。指定すると、その品目CDだけ。完全一致）
- 返す: `final_item_code`, `version`, `process_str`（A1 と同じ作り方）

#### A3. 品目工程マスタ＋加工機名（`DATA_RES_CAPA`＋`MSTR_RES` の代わり）
チェック項目入力（`check_input`）が、自分の SQLite（`kouteizuban`）へ写すのに使う。

- `GET /machining-schedule/api/genpinhyo/process-master/`（URL名 `machining_schedule:api_genpinhyo_process_master`）
- 返す（全件）:

| 項目 | 元 | KRD の列 |
|---|---|---|
| `final_item_code` | `SimpleMasterRow.final_item_code` | `FINAL_ITEM_CODE` |
| `version` | `version` | `VERSION` |
| `process_order` | `process_order` | `PROCESS_ORDER` |
| `process_code` | `process_code` | `PROCESS_CODE` |
| `res_code1` | `res_code1` | `RES_CODE1` |
| `res_name1` | 資源マスタで `res_code1` を引いた `Resource.name`。無ければ `""` | `MSTR_RES.NAME` |

- `process_order` が空欄の行（新規登録が必要な品目）は返さない。
- ⚠ 現品票側（`check_input`）は「KRD から消えた工程を自分の表から削除する」処理を持つ。
  - 0件のときは中止する、など安全弁がある。
  - API が0件や失敗のときは、空の一覧ではなく**エラー（5xx）**を返すこと。空の一覧と区別できないと、現品票側が全削除に進みかねない。

#### A4. 資源マスタ（`MSTR_RES` の代わり）
- `GET /machining-schedule/api/genpinhyo/resources/`（URL名 `machining_schedule:api_genpinhyo_resources`）
- 返す: `code`, `name`（全件）
- ⚠ A3 で加工機名を付けて返すなら、現品票側では使わない可能性がある。
  単体でも要るかどうかは現品票側の改修で決める。不要なら作らなくてよい。

#### （参考）優先VER・メッキの一覧は単独の API にしない
A1 の中で解決して返すので、現品票側に生の一覧は渡さない。

### 4-B. `apps/kouteizu`

#### B1. 図番（`DATA_KOUTEIZUKAN` の代わり）
- `POST /kouteizu/api/genpinhyo/drawings/`（URL名 `kouteizu:api_genpinhyo_drawings`）
  - 現品票発行・手入力発行・チェック項目入力の参考表示が使う。
  - 送る: `{"items": ["740-409CA300", ...]}`（加工部番＝rBOM の品目CDのままの形）
- `GET /kouteizu/api/genpinhyo/drawings/?q=<文字>&match=prefix|contains`（同じ URL名でメソッドを分けるか、別の URL名にする）
  - チェック項目入力の「部番で検索」が使う。KRD では `SETU_F LIKE` で探していた。
  - 件数の上限を設ける（例 1,000件）。
- 返す（1品目1行）:

| 項目 | 中身 |
|---|---|
| `item` | 送られた加工部番（GET のときは見つかった品目CD） |
| `matched_by` | `item_code2`／`item_code`／`none`（見つからない） |
| `B1` `B2` `F1` `F2` `L` `R` `C` | 図番（前詰め。**システムが使うのはこの7つ**） |
| `手書き` | `@` の図番（`ProcessDrawing.at_mark`） |
| `予備1`〜`予備4` | 7つの枠からあふれた図番 |

（キー名を英字にするなら、`B1 B2 F1 F2 L R C handwritten spare1..spare4` など。決めたら現品票側に合わせてもらう）

##### 4-B-1. 前詰めのルール（D8〜D10）
Django の列と現品票の列は、番号が対応しているわけではない。**記号ごとに、値のある列を番号の小さい順に詰める。**

| 記号 | Django の列 | 現品票の枠 |
|---|---|---|
| B | b1〜b8 | B1・B2（2つ） |
| F | f1〜f11 | F1・F2（2つ） |
| L | l1〜l5 | L（1つ） |
| R | r1〜r2 | R（1つ） |
| C | c1〜c2 | C（1つ） |

- 例: b1 空・b2 空・b3 あり・b4 空・b5 あり → B1 = b3、B2 = b5。
- 枠に入りきらない図番は、**B → F → L → R → C の順、その中は番号の小さい順**で、予備1から入れる。
  - 例: F が4つ（f1〜f4）で L が2つ（l1・l2）の品目 → F1=f1、F2=f2、L=l1、予備1=f3、予備2=f4、予備3=l2。
- 予備4つにも入りきらない分は捨てる。
- `@`（`at_mark`）は予備ではなく `手書き` に入れる。
- 値は Django の図番そのまま（記号付き。例 `00-1016B-F1`、`5516-409AA$$-R1`）。
- 実データでの確認（開発機・2026-09-28 取り込み分 63,958品目）:
  - あふれ0: 63,735品目、1: 216、2: 2、3: 3、4: 2、**5以上: 0**。予備4つで欠落は出ない。

##### 4-B-2. 記号の扱い（D9）
- Django の記号をそのまま正とする。R の図番は R、L の図番は L に入れる。
- KRD は「別部番の図面を流用する」値を持っていた（例: 部番 `TS-5613AA380` の R に `5516-409AA38`）。
  - その多くは、Obbligato 側で共通図面（`5516-409AA$$-R1`）として紐づいており、Django にも入っている。
  - 紐づいていない分は空欄になる。これで良しとする（KRD では格納がずれていたと聞いているため）。
  - 2026年1月の加工伝票の 504部番では、R が92部番、L が19部番、KRD にだけ値があった。

##### 4-B-3. 品目の引き方（D12）
- **品目CD2（`item_code2`）で先に引き、見つからなければ品目CD（`item_code`）で引く。**
- 普通の品目は 品目CD2 ＝ 品目CD なので、どちらで引いても同じ行になる。
- 例外（実データで4件）: ある品目の品目CD2 が、別の行の品目CD と同じ値になっている。
  - 例 `740-409B30` で引くと、品目CD2 では `740-409B300` の行（R1 あり）、品目CD では `740-409B30` の行（R1 なし）に当たる。
  - 利用者の判断で **品目CD2 の行（図番が多い方）を採る**。
- `item_code2` は一意ではない（現状は重複0件）。重複した場合は `item_code` の昇順で先頭を採る。

##### 4-B-4. Obbligato から消えた品目
`is_active=False` の扱いは「6. 要確認事項」の Q2。
